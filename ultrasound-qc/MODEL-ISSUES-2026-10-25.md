# 2026-10-25 模型阶段失败诊断与拟修复范围

最初诊断阶段只作只读排查。随后用户已明确确认实施修复，模型请求、引用校验、分区与失败提示已更新并重打包，详见 `FIX-2026-10-25.md`。以下保留最初诊断依据。

## 现象与结论

两类失败均发生于 model 阶段，OCR 已产出 10/11 个文本项。只读统计相应留档，正文合计约 184/211 个字符，不能把错误简单解释为报告过长。

### 模型输出被截断

`electron/deepseek.ts` 将 `max_tokens` 固定为 6000，未显式指定思考模式或强度；收到 `finish_reason=length` 时拒绝结果。该拒绝行为正确，不能把不完整 JSON 当作质控完成。

DeepSeek 官方说明当前默认开启思考，强度为 high；输出达到限制会返回 length。现有记录没有保存 finish reason、token usage 或被拒的模型响应，因此本轮无法确定上述失败中思考和最终正文各占多少 token；不能断言全部预算都被思考消耗。

### 模型摘录与原文不符

当前校验要求 quote（去掉空白后）出现在对应 sourceIds 的原文中。改数字、改文字、添加省略号或跨段自加连接词，均可能被拒绝；这是必要的证据保护。

另已独立复现程序一致性问题：`preparePayload` 可能移除分区标题或脱敏，但 `DeepSeekClient.review` 只按发送的 sourceId 筛选原 OCR 文档，未统一替换为实际发送文字。确认预览路径已替换文字，自动路径却可能使用另一个基准。

纯合成复现：原 OCR 两块分别为“超声所见：左肾轮廓清晰。”和“超声提示：右肾轮廓清晰。”；实际发送为去标题后的两个句子。模型引用两句连续文字时，自动路径会因原文中间夹有未发送标题而误拒；确认路径使用发送文字则通过。相反，模型引用未发送的“超声提示”在旧自动路径中可能错误通过。

本次实际失败留档中发送文字与保存的文档文字没有差异；上述缺陷不能直接当作这张截图的已证实原因。旧代码未留存被拒摘录，暂不能回溯到底改写或拼接了哪些字符。

## 最初修复方案（已确认实施）

1. 保留当前 deepseek-flash，显式配置思考强度与合理输出预算。建议先验证 low 思考强度和 16384 token 上限，并要求简洁 JSON；参数需通过合成正常、错字、单位、数量级和内部矛盾案例验证。提高输出上限可能增加单次费用与等待时间，不作自动收费重试。
2. 统一以“实际发送的 payload 文字”校验返回摘录，保留 OCR 定位信息；自动发送与人工确认使用相同基准。
3. 明确 quote 从一条真实来源中逐字复制连续片段，多处证据的解释放 reason，不拼接省略号或改写摘录。继续拒绝虚构位置、数字变化、无证据结果和纯空白摘录。
4. 记录必要的完成原因、token 用量和校验失败位置，避免下次只有通用错误。诊断保存在本机，不记录 API 密钥或模型内部思考全文。
5. 修正失败后仍显示“等待报告质控”的默认占位文案，使其反映任务已失败、需要手动重试。保留既有布局。

以上涉及模型请求、输出引用约定和失败提示，超出前次仅恢复运行环境的工作范围。医学质控标准、隐私过滤、历史留档和原文核对保护不应放宽；不得通过接受半截 JSON、忽略数字标点或失败标绿来消除报错。
